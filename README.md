# tg-chat-leads

Сбор лидов из открытых телеграм-чатов от лица живого аккаунта: читает чаты,
в которых ты состоишь, вылавливает тех, кто рекламирует там свои услуги,
и складывает уникальным списком в Postgres.

Собран за один вечер под конкретную задачу — найти частных преподавателей
для [TeachTrack](https://teachtrack.ru). Выложен как база, от которой можно
оттолкнуться под свою нишу.

> **In short (EN):** a NestJS + Postgres tool that reads public Telegram chats
> via a user account (MTProto/GramJS), detects people advertising their own
> services, deduplicates them into a lead list, and helps you contact them
> manually. Built in one evening. **Read the
> [postmortem](docs/postmortem-spam-ban.md) before enabling the sender** —
> automated outreach got the account spam-limited after 22 messages.

---

## Сначала прочитай это

В инструменте есть автоматическая рассылка. **Она не работает, и включать её
не надо.** Реальные цифры:

- 22 сообщения подряд → аккаунт ограничен. Причём **не автоматикой**: @SpamBot
  сообщил, что живые получатели пожаловались, а модератор жалобу подтвердил;
- на следующий день после снятия: 22 → 9 → 10 → 3 → 4 → 0. `PEER_FLOOD` —
  это не бан, а кран, который закручивают всё сильнее с каждым всплеском;
- итог: 208 отправленных, 2 ответа. Один процент.

Разбор целиком — [docs/postmortem-spam-ban.md](docs/postmortem-spam-ban.md).
Поэтому `SEND_DRY_RUN=true` стоит по умолчанию: из коробки рассылка ничего
не отправляет, только показывает, кому и что ушло бы.

**Полезная часть — сбор.** Он экономит часы и никого не беспокоит: люди сами
публикуют объявления в открытых чатах, чтобы их нашли.

## Что получилось на реальных данных

| | |
|---|---|
| чатов | 2 |
| прочитано сообщений | 4244 |
| собрано людей | 352 |
| из них «ищу репетитора» | **0** |
| время первого прогона | 35 секунд |

Последняя строка — самое важное. Примерно половина сообщений в таких чатах
это обратная сторона: «ищу репетитора для дочки», «требуется преподаватель
в наш центр». Первое — родитель, второе — работодатель, и ни тот ни другой
нам не нужен. Без стоп-слов список наполовину состоял бы из них.

## Почему userbot, а не бот

Обычный бот через Bot API не видит историю чата и по умолчанию не получает
чужие сообщения в группах. «Прочитать, кто и что писал за последние пару
тысяч сообщений» решается только от лица живого аккаунта. Отсюда GramJS
(`telegram`) и строка сессии вместо токена от BotFather.

## Быстрый старт

```bash
yarn install

# postgres в docker, порт 5434
yarn db:up

cp .env.example .env
# заполни TG_API_ID и TG_API_HASH — my.telegram.org → API development tools
# и TG_PHONE — телефон отдельного аккаунта, не основного

# разовый вход: спросит код из Telegram (и пароль 2FA)
yarn session:create
# напечатает длинную строку → положи её в .env как TG_SESSION

# впиши чаты: SCAN_CHATS=@chat_one,@chat_two
# аккаунт должен УЖЕ состоять в них — скрипт никуда не вступает

yarn typeorm migration:run
yarn start:dev
```

Дальше во втором терминале:

```bash
yarn refresh
```

## Ежедневный сценарий

`yarn refresh` делает три шага строго в этом порядке:

1. **дочитывает чаты** — только сообщения новее прошлого раза, курсор лежит
   в базе, простой ничего не теряет;
2. **сверяется с твоей личкой** — все, кому ты уже писал с этого аккаунта,
   уходят из списка;
3. **печатает, кому писать сейчас** — ник, ссылка и первая строка объявления,
   чтобы было чем зацепиться в первом сообщении.

Порядок не переставляй: если сверять личку до скана, свежедобавленные люди
её не пройдут и ты рискуешь написать человеку второй раз.

```
Кому писать сейчас: 110 чел. (показываю 30)

  1  @example_tutor  ·  score 6  ·  08.08  ·  t.me/example_tutor
     Репетитор по английскому (подготовка к ОГЭ/ЕГЭ). Добрый день! Меня зовут…
```

Написал — сразу отметь: `yarn wrote @nick1 @nick2`. Не подошёл —
`yarn skip @nick1`.

Отмечать надо руками, и это осознанно. Сверка с личкой ловит переписку, но
только пока она существует: человек может удалить диалог «у обоих», и на
твоей стороне не останется ничего. Источник правды — твоя база, а не
состояние Telegram, которое ты не контролируешь.

### Ответы на входящие

    yarn inbox          # выгрузит неотвеченное в inbox/<стамп>.md
    # попроси ассистента прочитать файл и написать ответы
    # в outbox/<тот же стамп>.md — правила в docs/reply-guidelines.md
    yarn outbox         # предпросмотр: что и кому уйдёт
    yarn outbox:send    # отправка

Директивы в outbox: `SEND` + текст, `CLOSE` (пометить отвеченным, ничего не
слать), `ASK` + вопрос (оставить себе). Перед каждой отправкой история
диалога перечитывается: если человек написал ещё раз или ты ответил руками —
запись пропускается.

## Как устроена эвристика

Каждое сообщение получает score:

| сигнал | баллы |
|---|---|
| профессия или предмет (`репетитор`, `вокал`, `английск`, …) | +2 |
| предложение услуги (`набираю`, `свободные окна`, …) | +1 |
| цена (`руб`, `₽`, `стоимость`, …) | +1 |
| контакт (`в лс`, `t.me/`, `@ник`, телефон) | +1 |
| длинное сообщение (150+ символов) | +1 |
| **стоп-слово** (`ищу репетитора`, `вакансия`, …) | **score = 0** |

Порог — `AD_MIN_SCORE` (по умолчанию 3), списки расширяются через
`AD_EXTRA_KEYWORDS` и `AD_EXTRA_STOP_WORDS`. Что именно сработало,
сохраняется в `matched_keywords` — по этому полю и надо крутить пороги,
а не наугад.

Под свою нишу правится в одном файле:
[`src/modules/scanner/ad-detector.ts`](src/modules/scanner/ad-detector.ts).

## Как не словить ограничение при сборе

Чтение чатов, в которых ты состоишь, — обычная активность клиента, и само
по себе безопасно. Осторожность зашита в дефолты: пауза между запросами
истории, разброс между чатами, потолок сообщений на проход, автосон при
коротком `FloodWait`.

Опасна не эта часть, а рассылка. См. постмортем.

## API

Всё слушает `127.0.0.1`. Если задан `API_TOKEN`, каждый запрос должен нести
заголовок `x-api-token` (кроме `/health`).

| метод | путь | что делает |
|---|---|---|
| POST | `/outreach/refresh` | `yarn refresh` — скан + сверка + список, текстом |
| GET | `/outreach/next` | `yarn leads` — только список |
| POST | `/outreach/mark` | `?usernames=@a,@b&status=skip` |
| GET | `/chats` | группы из диалогов аккаунта + готовая строка `SCAN_CHATS=` |
| POST | `/scan/run` | полный проход по чатам, в фоне |
| GET | `/scan/status` | курсоры и итог последнего скана |
| POST | `/leads/sync-contacted` | отсеять тех, кому уже писал |
| GET | `/leads/export.csv` | выгрузка с фильтрами |
| GET | `/send/status` | суточный бюджет, журнал попыток, планировщик |
| GET | `/account/status` | не ограничен ли аккаунт (спрашивает @SpamBot) |

## Как это построено

Весь инструмент собран за один вечер: 16 коммитов, 62 теста, NestJS +
TypeORM + Postgres + GramJS.

Дело не в скорости печати. Работало то, что у агента был **пример, от чего
оттолкнуться**: два старых проекта с похожей задачей и файл
[`CLAUDE.md`](CLAUDE.md) — договорённости проекта, которые агент читает
первыми. Там записано не «как писать код», а решения, которые нельзя
откатывать молча: почему дедуп живёт в базе, почему уникальность по
telegram id, а не по нику, почему стоп-слова обнуляют score целиком.

Этот файл оставлен в репозитории намеренно — он и есть та самая база.
Берите как образец под свою задачу, необязательно про Telegram.

Багов при этом было достаточно, и они в истории коммитов: `[rows, count]`
вместо массива строк от TypeORM на `UPDATE`, `inconsistent types deduced`
на переиспользованном параметре, `findByIds` без гарантии порядка. Быстро
не значит без ошибок — значит, что ошибки находятся и чинятся в тот же день.

## Персональные данные и правила Telegram

Собранные ники, имена и тексты объявлений — персональные данные третьих лиц.
База локальная, наружу не смотрит, выгрузки в `.gitignore`. Работаешь
из России — собирая такую базу, ты становишься оператором персональных
данных со всеми обязанностями.

Массовая рассылка незнакомцам нарушает правила Telegram, и аккаунт за неё
ограничивают. Инструмент это не обходит и не пытается: он останавливается
и говорит, что произошло.

См. [SECURITY.md](SECURITY.md).
