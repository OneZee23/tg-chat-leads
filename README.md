# teach-track-leadgen

Сбор лидов для TeachTrack из телеграм-чатов преподавателей. Работает от
**твоего личного аккаунта** (MTProto / userbot), читает сообщения в чатах, где
аккаунт уже состоит, вылавливает тех, кто рекламирует собственные услуги
репетитора/преподавателя, и складывает их в Postgres уникальным списком.

Рассылка — **руками**. Инструмент только собирает и сортирует.

---

## Почему userbot, а не бот

Обычный бот через Bot API не видит историю чата и по умолчанию не получает
чужие сообщения в группах. Задача «прочитать, кто и что писал за последние
пару тысяч сообщений» решается только от лица живого аккаунта. Поэтому GramJS
(`telegram`) и строка сессии, а не токен от BotFather.

## Быстрый старт

```bash
# 1. Зависимости
yarn install

# 2. База (только postgres, порт 5434 — 5432 и 5433 уже заняты другими проектами)
yarn db:up

# 3. Конфиг
cp .env.example .env
#    заполни TG_API_ID и TG_API_HASH — берутся на my.telegram.org
#    → API development tools (заводятся один раз на аккаунт)
#    и TG_PHONE — телефон того самого отдельного аккаунта

# 4. Вход в аккаунт: скрипт спросит код из Telegram (и пароль 2FA)
yarn session:create
#    напечатает длинную строку → положи её в .env как TG_SESSION

# 5. Впиши чаты в SCAN_CHATS (через запятую), например:
#    SCAN_CHATS=@teachers_chat,@repetitory_chat
#    ВАЖНО: аккаунт должен уже состоять в этих чатах. Скрипт никуда не вступает.

# 6. Миграции + запуск
yarn typeorm migration:run
yarn start:dev
```

## Ежедневный сценарий

Одна команда. Приложение должно быть запущено (`yarn start:dev`), команда
даётся во втором терминале.

```bash
yarn refresh
```

Она делает три шага строго в этом порядке:

1. **дочитывает чаты** — только сообщения новее прошлого раза, курсор лежит
   в базе, ничего не перечитывается;
2. **сверяется с твоей личкой** — все, кому ты уже писал с этого аккаунта,
   уходят из списка. В том числе те, кому ты написал час назад;
3. **печатает, кому писать сейчас** — ник, ссылка и первая строка объявления,
   чтобы было чем зацепиться в первом сообщении.

Порядок не переставляй: если сверять личку до скана, свежедобавленные люди её
не пройдут, и ты рискуешь написать человеку второй раз.

Просто посмотреть список, без похода в Telegram:

```bash
yarn leads
```

Написал — сразу отметь:

```bash
yarn wrote @nick1 @nick2
```

Кто не подошёл (агентство, перекуп, не преподаватель) — убрать навсегда:

```bash
yarn skip @nick1 @nick2
```

### Почему отмечать надо руками, хотя есть сверка с личкой

Сверка ловит переписку по твоим исходящим сообщениям — но только пока эта
переписка существует. Собеседник может удалить диалог **«у обоих»**, и тогда
на твоей стороне не остаётся ничего: ни сообщений, ни самого диалога. Сверка
такого человека не увидит, и он вернётся в список как новый, а ты напишешь
ему второй раз.

Поэтому источник правды — эта база, а не состояние Telegram: его
контролируешь не ты. `yarn wrote` ставит отметку, которую снаружи удалить
нельзя. Сверка с личкой остаётся страховкой на случай, когда отметить забыл.

Если нужен не список в терминале, а таблица:

```bash
curl -s 'http://127.0.0.1:3010/leads/export.csv?status=new&hasUsername=true' > leads.csv
open leads.csv
```

## Как это работает

**Два независимых канала сбора.**

*Исторический скан* (`POST /scan/run`) идёт по истории чата. Первый проход
берёт последние `SCAN_INITIAL_LIMIT` сообщений (по умолчанию 2000) — уходить
на годы назад смысла нет, объявления протухают. Дальше сохраняется курсор
(`tg_scan_state.last_message_id`), и следующие проходы читают только новое.

*Live-режим* (`LISTEN_ENABLED=true`) слушает новые сообщения в реальном
времени, пока приложение запущено.

Каналы спокойно уживаются: дедуп делает уникальный индекс в Postgres по
`tg_user_id`, а не код.

**Эвристика.** Каждое сообщение получает score:

| сигнал | баллы |
|---|---|
| профессия/предмет (`репетитор`, `вокал`, `английск`, …) | +2 |
| предложение услуги (`набираю`, `свободные окна`, …) | +1 |
| цена (`руб`, `₽`, `стоимость`, …) | +1 |
| контакт (`в лс`, `t.me/`, `@ник`, телефон) | +1 |
| длинное сообщение (150+ символов) | +1 |
| **стоп-слово** (`ищу репетитора`, `вакансия`, …) | **score = 0** |

Стоп-слова — самое важное. В чатах преподавателей половина сообщений это
«ищу репетитора для сына» и вакансии от школ; такие люди нам не лиды.

Порог задаётся `AD_MIN_SCORE` (по умолчанию 3), списки расширяются через
`AD_EXTRA_KEYWORDS` / `AD_EXTRA_STOP_WORDS`. В `matched_keywords` видно, что
именно сработало — по этому полю и надо крутить пороги, а не наугад.

## Как не словить бан

Telegram банит не за чтение, а за массовые сообщения незнакомцам. Чтение
истории чата, в котором ты состоишь, — обычная активность клиента. Но
осторожность зашита в дефолты:

- `SCAN_WAIT_TIME_SEC=2` — пауза между запросами истории внутри чата;
- `SCAN_DELAY_BETWEEN_CHATS_SEC=15` + случайный разброс сверху;
- `SCAN_MAX_MESSAGES_PER_RUN` — потолок на проход;
- `TG_FLOOD_SLEEP_THRESHOLD=120` — короткий FloodWait GramJS пересидит сам,
  длинный остановит скан этого чата (в `tg_scan_state.last_error` будет видно).

Опасная часть — не сбор, а **рассылка**. Она здесь не автоматизирована
намеренно: писать надо руками, малыми порциями, с живым текстом. Свежий
аккаунт, разослав 30 сообщений незнакомцам за час, уезжает в спамблок.

## API

Всё слушает `127.0.0.1` по умолчанию. Если задан `API_TOKEN`, каждый запрос
должен нести заголовок `x-api-token` (кроме `/health`).

| метод | путь | что делает |
|---|---|---|
| POST | `/outreach/refresh` | `yarn refresh` — скан + сверка с личкой + список, текстом |
| GET | `/outreach/next` | `yarn leads` — только список, текстом |
| POST | `/outreach/mark` | `?usernames=@a,@b&status=skip` — пометить по никам |
| GET | `/chats` | все группы и каналы из диалогов аккаунта + готовая строка `SCAN_CHATS=` |
| POST | `/scan/run` | полный проход по всем `SCAN_CHATS`, в фоне |
| POST | `/scan/run-one` | `{"chat":"@some_chat"}` — один чат синхронно |
| GET | `/scan/status` | идёт ли скан, итог последнего, курсоры по чатам |
| POST | `/leads/sync-contacted` | пометить `contacted` тех, кому уже писал из этого аккаунта |
| GET | `/leads` | список с фильтрами `status`, `minScore`, `chat`, `hasUsername`, `search`, `limit`, `offset` |
| GET | `/leads/stats` | сколько лидов в каждом статусе |
| GET | `/leads/export.csv` | те же фильтры, отдаёт CSV (с BOM, Excel открывает нормально) |
| PATCH | `/leads/:id/status` | `{"status":"contacted","note":"…"}` |

Статусы: `new` → `to_contact` → `contacted` → `replied` → `registered` /
`rejected` / `skip`. Двигаешь руками по мере работы.

### Чтобы не написать человеку дважды

```bash
curl -XPOST http://127.0.0.1:3010/leads/sync-contacted | jq
```

Проходит по личным диалогам аккаунта и помечает `contacted` всех, с кем уже
есть **твоё исходящее** сообщение. Просто существование диалога не считается:
человек мог написать первым, а ты не ответить.

Трогает только лидов в статусе `new` — руками проставленные `replied`,
`registered`, `skip` автоматика не переписывает.

После этого в выгрузку берёшь только нетронутых:

```bash
curl -s 'http://127.0.0.1:3010/leads/export.csv?status=new&hasUsername=true' > leads.csv
```

Два ограничения, о которых надо знать:

- смотрятся диалоги **того аккаунта, под которым сейчас залогинен**. Если
  прошлый аутрич шёл с другого аккаунта — подставь его `TG_SESSION`, прогони
  `sync-contacted`, верни обратно;
- глубокая проверка читает последние `CONTACTED_DEEP_LIMIT` (50) сообщений
  диалога. Если ты написал один раз, а человек потом прислал сотню — не
  увидим. После холодного аутрича переписки короткие, так что на практике
  почти не встречается.

## Схема

`tg_lead` — сам список. Уникальность по `tg_user_id`, а не по `@username`:
ник человек меняет когда захочет, а у части людей его нет вовсе.

`tg_scan_state` — курсор по каждому чату. Чтобы сбросить и перечитать чат
заново:

```sql
DELETE FROM tg_scan_state WHERE chat_ref = '@some_chat';
```

---

## Про персональные данные

Собранные ники и имена — персональные данные третьих лиц. Практика:

- база локальная, наружу не торчит (`HOST=127.0.0.1`), `.env` и `*.csv`
  в `.gitignore`;
- не тащить выгрузки в облака и чаты;
- в первом сообщении человеку сразу давать возможность отказаться и не
  писать повторно после отказа (статус `rejected` для этого и есть);
- удалять то, что не пригодилось, а не копить годами.

## Про библиотеку

`telegram` (GramJS) 2.26.x при установке пишет, что пакет заархивирован, и
предлагает форк `teleproto`. Работать он не перестал, и именно он крутится
в двух рабочих проектах, с которых списан этот. Если однажды сломается —
переезд на `teleproto` заявлен как почти полностью совместимый.
