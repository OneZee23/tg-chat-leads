# Два телеграм-аккаунта в лидгене

**Дата:** 2026-09-14
**Статус:** реализовано 14.09.2026 (код есть, вторая сессия ещё не заведена)

## Зачем

Telegram пускает примерно 40–50 сообщений в сутки НОВЫМ людям (тем, кого
нет в контактах). Это потолок не наш, а платформы, и обойти его нельзя —
можно только добавить второй аккаунт. Тогда дневная ёмкость удваивается
без изменения темпа у каждого из них, то есть без роста риска.

В очереди сейчас 636 собранных лидов, которым ещё не писали. При 45 в
сутки это две недели, при 90 — одна.

## Чего нельзя сделать наивно

**Два процесса на одну сессию убивают сессию.** Это уже происходило
07.09.2026 и стоило аккаунта. Поэтому: один процесс, несколько клиентов,
у каждого СВОЯ строка сессии. Никаких вторых экземпляров приложения.

**Ответы приходят тому, кто писал.** Если второй аккаунт отправит
сообщение, а инбокс собирается только с первого, ответ этого человека мы
не увидим никогда. Значит сбор диалогов обязан читать все аккаунты —
иначе фича не экономит время, а теряет живых людей. Это не улучшение
«потом», это условие запуска.

**Один лид — один аккаунт навсегда.** Если сегодня человеку написал
аккаунт A, а через неделю с фоллоу-апом придёт B, для человека это два
незнакомца с одинаковым текстом. Аккаунт закрепляется за лидом при первой
отправке и дальше не меняется.

## Решение

### Данные

```
tg_send_attempt += account varchar(32) NOT NULL DEFAULT 'main'
tg_lead         += assigned_account varchar(32) NULL
```

`assigned_account` пустой, пока лиду не написали. Существующие отправки
помечаются `main` — они и правда все с основного аккаунта.

### Конфигурация

`TG_SESSION` остаётся основным аккаунтом, как сейчас. Дополнительные:
`TG_SESSION_2`. Пустая переменная означает «аккаунта нет» — приложение
поднимается с одним, как и раньше.

Имена аккаунтов фиксированные: `main` и `second`. Свободные имена в env
дали бы разъезд между строкой в базе и строкой в конфиге, а сверять их
нечем.

### Пул клиентов

`TelegramAccountsService` поднимает все заданные сессии и держит их
рядом. Существующий `TelegramClientService` остаётся тем, чем был, —
основным аккаунтом для чтения: сканер чатов, ресерч, статус. Их логику
не трогаем.

Для ОТПРАВКИ аккаунт выбирается так:

1. Если у лида уже есть `assigned_account` — только он. Даже если у него
   кончился дневной лимит: тогда лид ждёт, а не переходит к другому.
2. Иначе — аккаунт с наибольшим остатком дневного лимита.
3. Если у всех лимит исчерпан — не отправляем.

### Лимит

Дневной потолок `SEND_MAX_PER_DAY` начинает считаться **на каждый
аккаунт**, а не на всех сразу. Смысл переменной меняется, и это
осознанно: потолок защищает аккаунт от бана, а банят аккаунт, а не
инструмент.

Окно остаётся скользящим (24 часа), как сейчас.

### Сбор диалогов

`dialogs.service` читает диалоги каждого аккаунта и помечает, где найден
ответ. В инбоксе у записи появляется строка, с какого аккаунта шла
переписка, — иначе отвечать придётся вслепую.

Отправка ответа идёт тем же аккаунтом, который вёл переписку.

## Риски

| Риск | Что делаем |
|---|---|
| Второй аккаунт свежий → банят быстрее | Владелец берёт прогретый, с историей и контактами. Проверка при старте: аккаунт авторизован и у него есть диалоги |
| Один человек получает два сообщения от разных аккаунтов | `assigned_account` закрепляется при первой отправке |
| Ответы на второй аккаунт теряются | Сбор диалогов со всех аккаунтов — часть этой же работы, не «потом» |
| Оба аккаунта шлют одновременно и выглядят как ботнет | Отправка последовательная, паузы с джиттером сохраняются; параллельной отправки НЕ добавляем |
| Сессия второго аккаунта утекает в git | `.env` уже в `.gitignore`; в `.env.example` только пустой placeholder |

## Чего НЕ делаем

- Параллельной отправки. Выигрыш в скорости не нужен: узкое место —
  дневной потолок, а не время.
- Больше двух аккаунтов. Механика на N рассчитана, но проверять будем на
  двух.
- Автоматической ротации при бане. Если аккаунт улетел, это разбирает
  человек.

## Как это вышло в коде

| Что | Где |
|---|---|
| Пул сессий, проверка «не тот же аккаунт», предупреждение о холодном | `src/modules/telegram/telegram-accounts.service.ts` |
| Выбор аккаунта под лида (правило + тесты) | `src/modules/sender/account-pick.ts` |
| Отправка: бюджет на аккаунт, закрепление, отчёт по аккаунтам | `src/modules/sender/sender.service.ts` |
| Обход диалогов по всем аккаунтам | `DialogsService.eachDialog` |
| Колонки `account` / `assigned_account` | `src/migrations/1780600000000-MultiAccount.ts` |
| Вход во второй аккаунт | `yarn session:create:second` |

Два отступления от дизайна выше, оба осознанные:

**Выбор идёт по числу отправленного, а не по остатку лимита.**
`SEND_MAX_PER_DAY` по умолчанию `0` — потолка нет, — и тогда остаток у всех
аккаунтов одинаково огромный. Правило «у кого больше остаток» молча свелось
бы к «всегда основной», и второй аккаунт не отправил бы ни одного сообщения.
При равном потолке «меньше отправил» и «больше осталось» — одно и то же.

**FloodWait считается по паре аккаунт+метод.** В дизайне этого не было.
Лимит Telegram выдаёт аккаунту; общий на двоих счётчик останавливал бы
отправку с того, кого никто не зажимал.

## Чего ещё нет

- Второй аккаунт не заведён: `TG_SESSION_2` пуст, всё работает как раньше,
  с одним. Код проверен тестами, но живой второй сессией — нет.
- `@SpamBot` опрашивается только про основной аккаунт: его ограничение
  останавливает запуск целиком. Это осознанно — автоматической ротации при
  бане здесь нет, такое разбирает человек.
